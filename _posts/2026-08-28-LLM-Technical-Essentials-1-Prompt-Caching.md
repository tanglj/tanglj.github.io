大模型定价中，tokens 输入计价分为缓存命中、缓存未命中，缓存命中的价格通常只有未命中的 1/10 甚至更低。

比如 DeepSeek 的定价表（2026/8/28）：

![DeepSeek定价表](assets/posts-img/009-deepseek-pricing.png)

> 原文地址：[Deepseek API 文档：模型 & 价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)

那么什么是缓存命中，为什么能够有如此低的定价呢？

我们先看一个例子：客服对话质检——判断用户的问题是否得到了解决。这件事的判定标准很难一句话说清：用户回了“好的谢谢”算解决；机器人给了方案但用户没再回复，算不算；同一个问题追问三遍；最后转了人工——这些边界都得写进规范，还要配几个示例。

于是，每次调用都要发出去一份两千字左右的规范，加上一段三五百字的对话，模型只回一个标签和一句理由。如果有几万条对话，完整的任务跑完，那份两千字的规范会被发给大模型几万遍。

## 1. 缓存命中指的是什么

提示词缓存命中，指的是新请求的前缀与已经缓存的前缀匹配，模型可以复用这部分已经计算好的中间结果，而不必重新计算。

命中的判定是逐 token 的**前缀匹配**，不是语义相似，也不是关键词匹配。计费上的"缓存命中 token"，指的就是这部分被复用、未重新计算的输入 token。

"前缀"是字面意思：从第一个 token 开始，连续、不间断地对齐。质检任务的请求提示词拆开看是这样：

```text
[固定] 质检规范：判断用户问题是否已解决，判定标准如下……（约 2000 字）
[固定] 示例一、示例二、示例三……
──────── 以上部分每次请求完全相同 → 可命中 ────────
[变化] 待质检对话：用户：我的订单三天了还没发货 / 机器人：已为您催单……
[变化] 请输出标签和理由
```

上半部分每次一字不差，它就是可命中的前缀；下半部分每次都变，从对话开始的位置往后都算未命中。反过来，如果哪次把对话放到了规范前面，第一个 token 就对不上了，整个请求的命中率归零。

还有一个常见误解要先排掉：命中不代表返回的是旧答案。模型照样重新生成回复，省掉的只是"读题"的功夫。

提示词缓存按使用方式可分为**隐式缓存**与**显式缓存**两类，前者厂商自动生效、用户无感，后者需要手动标记缓存断点。

## 2. 提示词缓存有什么价值

对用户最直接的价值是**省钱**，长 system prompt 或长文档被反复使用时，成本差距会被显著放大。

回到质检任务算一笔。假设规范 2000 字、对话 500 字，即每次请求约八成内容是完全重复的，命中价按未命中价的 1/10 计：

| | 第 1 条 | 第 2 条起（每条） |
| :--- | :--- | :--- |
| 命中部分（80%） | 全额 | 按 1/10 计 |
| 未命中部分（20%） | 全额 | 全额 |
| 单条输入成本 | 1.0 | 0.2 + 0.8×0.1 = 0.28 |

也就是说输入这一项的总支出降到原来的三成左右，而代价只是把 prompt 的顺序理顺。重复内容占比越高、批量任务的量级越大，获得的折扣收益越大。

第二个价值是**降低首 token 延迟（TTFT）**，因为省掉的是最耗时的预填充阶段。前缀越长，这一项的改善越明显——一份几千 token 的规范，重新算一遍和直接取缓存出来，速度差很多。

对厂商而言，复用意味着同一张卡能服务更多请求，推理吞吐被有效提升。这也是缓存命中能定到如此低价的根本原因：它对厂商来说本来就便宜，让利给用户能换来更多可服务的请求量，双方都划算。

## 3. 提示词缓存的机制

工程上常把这类机制统称为 Prompt Caching，但从底层实现看，缓存的并不是原始 prompt 文本，而通常是模型处理这些输入后产生的中间状态，例如 KV Cache。不同厂商的具体实现可能不同。

模型在生成第一个 token 之前，需要先处理完整的输入，对每个 token 进行计算，这个阶段叫预填充（prefill）。它是计算密集的，输入越长越贵。缓存的就是这份中间结果。

关键在于一个性质：在因果注意力（Causal Attention）中，一个 token 的计算只依赖它自己以及它之前的 token，而不会依赖后面的 token。因此，只要前缀没有变化，这部分计算结果就可以复用；前缀发生变化时，从变化位置开始，后续相关计算通常需要重新进行。

两条推论直接由此而来：

- 只要开头的内容一字不变，这段开头对应的中间结果就可以原样取用，无需重算；
- 一旦前缀中间改动了一个 token，从该位置往后的缓存通常无法继续复用，而它前面的部分仍然有效。

三个请求对比一下就很清楚：

```text
请求 A   规范(2000字) │ 对话甲
         └─ 首次，全部计算 ─┘

请求 B   规范(2000字) │ 对话乙
         └─── 命中 ───┘└ 重算 ┘        省下 2000 字

请求 C   规范(第800字处改了一句) │ 对话甲
         └ 前800字命中 ┘└──── 之后全部重算 ────┘   只省下 800 字
```

可以想象垒积木：从下往上垒，抽掉中间一块，上面的塌了，下面的还稳稳立着。这就是为什么主流 Prompt Caching 机制通常围绕“前缀”设计，而不是任意位置的片段匹配——也是第 4 节大部分缓存优化技巧的基础。

命中后无需重新完成这部分前缀的主要计算，只需要读取并复用已经缓存的中间结果。相比重新进行完整的 prefill，计算成本和延迟都会明显下降，因此厂商可以把这部分输入 token 以远低于普通输入的价格计费。

再补两个工程上的事实，都会影响提示词缓存能不能真的命中：

- 有最小长度门槛。缓存按块存储，太短的前缀不值得缓存，通常不生效，具体门槛各家不同。
- 有有效期。一段时间无人使用就会被清理，间隔太久的调用必然未命中。

## 4. 利用提示词缓存节省 token 开支的技巧

核心原则只有一条：静态内容前置，动态内容后置。下面分三个场景给出做法，最后一节是需要留意的边界。

### 4.1 在组织 Prompt 时

开头不要放任何会变的东西。当前时间、批次编号、请求 ID、随机数，任意一个都能让整段前缀作废。有意思的是同一个东西放在不同位置结果相反：

```python
# ❌ 时间戳在规范之前 → 每次前缀都不同，后面 2000 字全部重算
system = f"当前时间：{now}\n\n{质检规范}"

# ✅ 时间戳挪到末尾 → 规范部分照常命中
system = 质检规范
user   = f"{对话内容}\n\n当前时间：{now}"
```

对话记录里自带的会话 ID、消息时间戳，放在后面完全无害；同样的时间戳写进开头的规范里，前面两千字每次都全部重新处理了。

示例要固定下来。按当前样本动态检索"最相似的几个示例"也许能提准确率，但它让前缀每次都不同，缓存全部失效，或许固定几个经典实例更划算。

序列化时保证键序稳定。不要依赖动态构造过程中不稳定的字段顺序。例如来自 `set` 的内容本身没有稳定顺序，或者多个数据源合并时字段插入顺序可能发生变化。对于需要长期复用的 JSON，应显式固定序列化顺序：

```python
# ❌ set 无序，每次序列化出的标签顺序可能变化
labels = {"已解决", "未解决", "无法判断"}

# ✅ 用有序结构，并固定 key 顺序
labels = ["已解决", "未解决", "无法判断"]
json.dumps(schema, ensure_ascii=False, sort_keys=True)
```

一段内容被多次追问时，它也是"静态"的。质检任务常常对同一段对话连问三个问题：是否解决、未解决的原因、责任归属。这时顺序应该是规范 → 对话 → 具体问题：

```text
❌ 规范 │ 问题1 │ 对话        三次调用只有规范(2000字)命中
✅ 规范 │ 对话 │ 问题1        第 2、3 次连对话(500字)一起命中
```

此外，还可以考虑到，改规范等于推倒重来，已有缓存全部作废。所以规范要先用小样本试跑调稳，再上大批量。

### 4.2 在调用 API 时

固定 messages 的结构和顺序，让 system prompt、固定示例、长文档始终排在前面，用户输入排在最后。顺序颠倒是最常见、也最容易被忽略的失误：

```python
# ❌ 命中率 0：变化的对话在最前面，规范反而在后
messages = [
    {"role": "user", "content": f"{对话内容}\n\n请按以下规范判断：\n{质检规范}"},
]

# ✅ 规范固定在前，对话追加在后
messages = [
    {"role": "system", "content": 质检规范},     # 每次完全一致
    {"role": "user",   "content": 对话内容},     # 每次变化
]
```

使用显式缓存的厂商，把缓存断点打在"稳定/变化"的交界处，也就是规范结束、对话开始的那个位置。注意断点数量通常有上限。

上线后从响应的 usage 字段核对，可以判断是否提升了缓存命中率：

```python
u = resp.usage
print(u.prompt_cache_hit_tokens, u.prompt_cache_miss_tokens)
# 命中率 = 命中 tokens / 输入 tokens 总数
```

改造前后各跑一批对比一次，就知道有没有真的生效。字段名各家不同，以官方文档为准。

批量接口与缓存折扣能否叠加，各家规则不一致，有的厂商在批量请求上不启用缓存。跑大批量之前查一下目标厂商的文档。

### 4.3 在构建 Agent 时

工具定义和系统指令放在最前面并保持稳定。工具列表顺序变化、临时增删一个工具，都会打断整个前缀：

```python
# ❌ 每次按需筛选工具，工具定义段每次都不同
tools = pick_tools_for(user_query)

# ✅ 全量工具、固定顺序
tools = ALL_TOOLS          # 顺序写死，不随请求变化
```

对话历史坚持 append-only：新内容往后追加，不要回头修改前面的轮次。工具返回的结果也追加在末尾，不要为了"整理上下文"重排前面的消息。

```text
第 1 轮  指令 │ 工具定义 │ Q1 │ A1
第 2 轮  指令 │ 工具定义 │ Q1 │ A1 │ Q2        ← 前面原样保留，全部命中
第 3 轮  指令 │ 工具定义 │ [Q1+A1 的摘要] │ Q2 │ A2 │ Q3
                         └─ 从这里开始全部重算 ─┘
```

中途对历史做摘要压缩，会使被压缩位置之后的原始前缀无法继续复用，因此后续请求通常需要从压缩点重新计算。压缩省下的上下文 token 和损失的缓存收益需要放在一起权衡。

RAG 场景把共享文档放在前面、个性化片段放在后面，并固定检索结果的排序（比如按文档 ID 排序而非按相似度分数，分数的微小抖动会改变顺序）。

### 4.4 边界与陷阱

- 只省输入，不省输出。缓存作用于预填充阶段，对生成阶段没有帮助。"长输入短输出"的活收益极大（质检、分类、文档问答），"短输入长输出"的活（写文章、写代码）几乎没有收益。
- 低频调用可能是负收益。显式缓存写入通常有额外费用，只调用十几次可能收不回成本，可能要跑上千上万次才划算。
- 命中率不是唯一目标。前面提到的动态示例检索就是典型冲突，该牺牲缓存的时候就牺牲，先看效果再看成本。
- 命中不等于结果相同。模型仍会重新生成，采样参数照常起作用，输出未必一致。缓存也不改变回答质量，别把它当成正确性或稳定性的保障。
- 各家规则差异大且变动快。最小前缀长度、有效期、断点上限、折扣比例，都以官方文档的当期版本为准。

## 5. 总结

提示词缓存的本质，是复用已经计算过的输入前缀，从而减少重复的 prefill 计算。

对开发者来说，最重要的不是“开启缓存”，而是让可复用的内容形成稳定前缀。

因此可以记住三句话：

1. 缓存复用的是输入前缀，不是模型的旧答案；
2. 稳定内容尽量前置，变化内容尽量后置；
3. 缓存命中率、上下文长度、模型效果和整体成本需要一起权衡。

在质检这类"长规范 + 短样本 + 大批量"的任务里，把顺序理顺往往就是一次改动、几行代码的事，输入成本可降到三成左右。这是大模型工程里非常值得优先考虑的优化之一，值得在项目一开始就设计好。
